# {{name}}

A Single Solution product (PLAN.md Part 0, 0.4): widgets and an API for merchants' websites, built on `@ss/app-kit`.
Generated by `ss app init`; the sample feature `notes` shows every part a feature has.

## Layout (PLAN 0.4.13)

| Folder      | What it holds                                                                                               |
| ----------- | ----------------------------------------------------------------------------------------------------------- |
| `core/`     | pure logic (no I/O, no DOM): `notes.js` checks a note; `widgets.js` names the widget global and attribute   |
| `server/`   | routes (`routes.js`), the public docs page (`docs.js`) and the generated widget bundle (`widget-script.js`) |
| `adapters/` | the kit wiring (`product.js`) and the merchant database (`notes-store.js`)                                  |
| `ui/`       | widgets on `@ss/app-kit/widget`: the visitor widget `note_form`, the admin widget `inbox`                   |
| `app/`      | Next.js: the API function `app/api/[...path]/route.js` and the dashboard page `app/dashboard/page.js`       |
| `strings/`  | `en.json`: every word the widgets show (merchants change them per website in Settings → Texts)              |
| `schemas/`  | each feature's settings schema (`manifest.json` points at it with `$ref`)                                   |
| `tests/`    | Vitest on the kit's fake Portal (`@ss/app-kit/testing`) and a test MongoDB                                  |
| `docs/`     | the public docs' texts (`guide.json`), served at `/docs`                                                    |

Imports go server → core | adapters, adapters → core, ui → core, never the reverse; `ss app validate` checks it.

## The sample feature `notes`

- `POST /v1/notes` (browser token): a visitor leaves a note. `GET /v1/notes` (server token): the merchant's server
  reads them. `GET /v1/admin/notes` (ticket with `notes.read`): the admin widget reads them.
- One setting, `maxLength` (Settings in the dashboard), within the hard maximum in `core/notes.js`.
- `/widget.js` is public and the same for every website. When its script tag has `data-token` it fetches the
  website's widget config (`GET /v1/widget/config`) and mounts the visitor widget into
  `<div data-ss-{{id}}="note_form"></div>`; on admin pages (no `data-token`) the page calls
  `window.{{global}}.admin({ getTicket })`, which fetches the config with the ticket and mounts the admin widget into
  `<div data-ss-{{id}}="inbox"></div>`. Off features, a stopped product or a missing database render nothing.
- Data rights: a visitor's notes are exported and deleted by e-mail (`adapters/product.js`).

To add a feature: add it to `manifest.json` (key, name, description, dependsOn, settings `$ref`), its settings
schema to `schemas/`, its routes with `feature: '<key>'`, its widget texts to `strings/en.json`, its guide to
`docs/guide.json` and its tests; then `pnpm build` (or `ss app assets`) regenerates `openapi.json` and the widget
bundle.

## Environment

Exactly three variables (`.env.example`): `MONGODB_URI` (this product's own database), `CONNECT_SECRET` and
`ENCRYPTION_KEY` (each random, at least 32 characters). `ss app init` wrote development values to `.env.local`
(git-ignored). Then connect the product in the Portal: Products → Add product, with its address and `CONNECT_SECRET`.

## Scripts

`pnpm dev` / `pnpm build` (both regenerate `openapi.json` and `server/widget-script.js` first) / `pnpm start`,
`pnpm check` (format, lint, typecheck, tests with coverage 90 % lines and functions, 85 % branches) and
`pnpm validate` (`ss app validate`).

## Composing the product in a system test

```js
import { createProductInstance } from '@ss/product-{{id}}/product';
import { createRoutes } from '@ss/product-{{id}}/routes';

const product = createProductInstance({ config, store, fetch, now, outbound, outboundSend });
const handler = product.handler(createRoutes(product), { after });
```
