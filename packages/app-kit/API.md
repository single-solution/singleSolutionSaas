# @ss/app-kit API

Five entries: `@ss/app-kit` (server), `@ss/app-kit/widget` (browser, no Node.js imports), `@ss/app-kit/headers`
(`next.config.js`), `@ss/app-kit/testing` and `@ss/app-kit/api` (API descriptions, for `ss` and tests; never loaded in
production).

### Route definitions

`defineRoute({ method, path, auth, feature?, permission?, database?, idempotent?, rateLimit?, rawBody?, maxBodyBytes?,
roles?, handler })`

- `auth`: `browser` (browser token in `Authorization: Bearer`; Origin required and allowed; CORS for it, which also allows the
  `SS-Sign-In`, `SS-Guest` and `SS-Order-Key` headers; without an Origin, the server token: a visitor call from the
  merchant's server with `SS-Visitor-IP`, required on writes, in its own window of 3,000 requests per minute per route
  per website plus the per-visitor limits), `server` (server token; refused with an Origin header; no CORS; optional
  `SS-Actor-*` headers name the acting user, 400 `invalid_actor` when malformed), `ticket` (ticket bound to the
  request's Origin; CORS for it), `dashboard` (session cookie), `portal` (a call the Portal signs with its pinned key
  for this product, method, path, query and body, used once: `@ss/protocol` `verifyPortalCall`; the website is
  `?websiteId=`, `ctx.websiteId` null when missing or malformed; any failure 401 `unauthorized`; no CORS), `none`.
- `feature` (browser, server, ticket): 403 `feature_off` while off; a list works while any of them is on; ticket routes
  default to their permission's feature.
- `permission` (ticket): the ticket must carry it.
- `database` (browser, server, ticket; default true): 403 `database_not_connected` until the `database` connection is
  saved.
- `idempotent`: a repeated `Idempotency-Key` for the same website and route within 24 hours gets the first answer
  again (status, headers and body, plus `Idempotent-Replayed: true`) when it is the same request (method, address,
  body, ticket user or acting user, `SS-Guest`, `SS-Order-Key`); another request under the key answers 409
  `duplicate_request`, and a repeat while the first still runs 409 `in_progress` with `Retry-After: 1`. A 5xx answer
  frees the key; answers larger than 64 kB are not kept (a repeat answers 409 `duplicate_request`).
- `rateLimit`: `{ limit, windowSeconds, per?: 'website' | 'visitor', bucket? }` or a list of them (code constants);
  routes with the same `bucket` share a counter. The per-visitor limits are checked first; a website-wide window counts
  only requests that passed them, so one address cannot use it up for every visitor (SE-2).
- `roles` (dashboard): `merchant`, `owner`, `support` (default all).

Every website route also checks the status: 403 `product_unavailable` with `reason` (stopped, suspended, removed), 503
`portal_unreachable` after 6 hours without the Portal (the status or the revocation list; `OFFLINE_GRACE_MS`), and 401 `invalid_token` for every token or ticket failure.
A status copy older than 5 minutes (but within the 6 hours) is used at once and fetched again, with the revocation
list, right after the response (one fetch per website at a time on an instance, at most every 30 s); only a website
with no copy it may use waits for the Portal, at most 5 s (`WAITED_FETCH_MS`), and so does the next use after a
`status.changed` notice. Dashboards wait for a copy older than 5 minutes (they show the status and today's charges).
A merchant or product database that cannot be reached, or does not answer within its deadlines (`DATABASE_DEADLINES`:
server selection and connection 5 s, a free pooled connection 10 s, each send or receive 10 s; pools of 5 per
database and instance), answers 503 `database_unavailable` with `Retry-After: 5`, never 500, and is used again by the
next request once it is back, on the same instance (`createMongoStore` connects its client before use and again after
a failed connect). A cold instance brings the product's merchant-database indexes up to its declaration once per
database, two collections at a time: the declared indexes are the truth, so in each collection the product declares
indexes for, an index no longer declared or declared with other keys or options (same name) is dropped and a missing
one is created; no record is changed (a query for `field: null` also matches a missing field, so a new field needs no
backfill), and another product's or an undeclared collection is never touched.

`ctx` (handler argument): `request`, `requestId`, `method`, `path`, `params`, `query`, `searchParams`, `headers`,
`idempotencyKey`, `body`, `rawBody`, `origin`, `websiteId`, `merchantId`, `status`, `token`, `ticket`, `actor` (K2),
`visitor` (`{ server, ip }`, K3), `clientIp`, `session`, `after(task)`, `data()` (the guarded merchant database), `log`.

| `POST …/business/refresh`                                                                                                                                          | dashboard                                        |
| `GET /v1/dashboard/defaults`, `PUT /v1/dashboard/defaults/:key` (`<feature>.<setting>`, `text.<key>`, `theme`, `format`; `{ value }`, `null` removes)              | dashboard, Owner                                 |
| `GET\|PUT /v1/dashboard/prices` (`{ prices: { key: millicreditsPerHour } }`)                                                                                       | dashboard, Owner                                 |
| `POST /v1/dashboard/reseal` → `{ keyId, previousKeyId, resealed, current, unreadable, failedWebsites }` (stored secrets sealed again with the current key)         | dashboard, Owner                                 |

Dashboard writes are refused unless their Origin is the product's own address; dashboard and `/sso` answers carry
`X-Frame-Options: DENY` and `Content-Security-Policy: frame-ancestors 'none'`.

### The Setup sheet part (`GET /v1/blueprint`)

The Portal gathers every product of a website into one Setup sheet (`ss.blueprint/1`); each product answers its part
from what the kit already keeps, for any status but `removed` (404 `website_not_found`; an unknown website too; 503
`portal_unreachable` when the status cannot be had): `{ productId, name, version, status (the effective one), docs:
{ guide, openapi }, business (the product's copy of business.json: found, fetchedAt, name, country, timeZone),
install: { scriptUrl, installed (a visitor widget seen in the last 7 days; null without a visitor widget on),
lastSeenAt }, features: [{ key, title, description, on, dependsOn, recommendFor, settings, lists }], shared, connections,
widgets, staffPermissions, events, checklist, summaries, build }`.

- A feature's `recommendFor` are its manifest's business profile rules (`@ss/contracts/profile`; empty without), so
  the Portal's advisor can recommend it from the website's business profile.

- A feature's `settings` (`{ key, title, value, default }`, `default: true` while the website has not saved its own
  value) and `lists` (`{ name, title, summary, count }`: an array counted, an object as `<member>: <size>` per list
  member; a list of several features shows under the first of them that is on) are filled only while it is on.
  `shared` lists shared settings while one of their features is on.
- `connections`: `{ key, title, kind, neededBy, needed, set, state, testedAt }` — never a value, its last characters or
  a test message.
- `widgets`: `{ key, kind, features, on, ready }`, `ready` = on, the product serving the website (active or grace) and
  the merchant database saved. `staffPermissions`: `{ key, name, feature, on }`. `events`: `<product>.settings.changed`
  when the product publishes events, plus the hook's types (each `<product>.<event>`).
- `checklist`: features switched on, each connection a switched-on feature needs, the widget script (with a visitor
  widget on) and business.json, each `{ key, done, text }`.
- `hooks.blueprint({ websiteId, merchantId, on })` may add `events`, `lists` (a summary in the product's own words by
  list name, at most 300 characters) and `summaries` (`[{ title, text }]`, at most 20); what does not fit is left out
  and logged, and a failing hook or list read never fails the answer.
- `build`: `[{ feature, what, docs }]` for each feature that is on and has a `build` text (the option), `docs` its
  section of the guide (`<docsUrl>#feature-<key>`).
- No secret can leave: besides never reading connection values into the answer, every string of the finished answer
  that holds a value saved in the website's Connections (`SECRET_MIN_LENGTH`, 8 characters or more; every text member
  of an object value) becomes `[hidden]` (`HIDDEN`), so a setting or hook text that repeats a key shows nothing of it.

**Switch on** (`POST /v1/blueprint/features?websiteId=`, also a signed Portal call): the Setup sheet's advisor switches
`features` on for the Owner or Support admin the Portal names (`admin: { id, name, role }`), each with every feature
it needs (`withDependencies`), through the same feature report as the dashboard's Features page: the Portal accepts it
only for a current Owner or Support admin, and Recent changes names the admin. It answers `{ version, on, added }`
(`added` empty, and nothing reported, when all were on already); 422 `validation_failed` with `errors` for another
admin or unknown features, 404 for a website the product does not serve, and the Portal's refusal as on the Features
page.
